## 2. Worktree/workspace identity model

- `Workspace` (`src/workspace.rs:176-207`) is the shared session/organizational unit. Key fields:
  - `pub id: String` — stable public workspace identity (`src/workspace.rs:178`), generated by
    `generate_workspace_id()` (`src/workspace.rs:107-110`) using a `w`-prefixed public-number
    alphabet (`decode_public_number`/`encode_public_number`, `src/workspace.rs:112-137`).
  - `pub worktree_space: Option<WorktreeSpaceMembership>` (`src/workspace.rs:196`) — the explicit,
    Herdr-managed link from a workspace to a git worktree grouping.
  - `identity_cwd: PathBuf` (`src/workspace.rs:182`) — fallback identity source when there's no
    git/worktree metadata.
- `WorktreeSpaceMembership` (`src/workspace.rs:33-39`):
  ```rust
  pub struct WorktreeSpaceMembership {
      pub key: String,            // stable group key, shared by all worktrees of one repo
      pub label: String,
      pub repo_root: PathBuf,
      pub checkout_path: PathBuf, // this worktree's own checkout path — closest thing to a worktree id
      pub is_linked_worktree: bool,
  }
  ```
  There is no separate numeric/opaque "worktree id" — the natural identity key for a worktree
  *as a service-registration target* is `(worktree_space.key, checkout_path)`, or simply the
  owning `workspace.id` since today one workspace ⇄ one worktree checkout 1:1 (`src/app/worktrees.rs:10-37`
  shows workspaces closing/switching 1:1 with worktree removal).
- Plain worktree git plumbing (`git worktree add/remove` command building, not persisted state)
  lives in `src/worktree.rs` — `ExistingWorktree` (`src/worktree.rs:13-19`, plain path+branch
  struct for `git worktree list --porcelain` parsing at `src/worktree.rs:422-489`) is a
  *filesystem-level* worktree view distinct from `WorktreeSpaceMembership` (the *session*-level
  grouping). Services attach to the session-level `WorktreeSpaceMembership`/`Workspace`, not to
  `ExistingWorktree`.
- Conclusion: **the identity key for service ownership is `workspace_id`.** A workspace that is a
  linked worktree already carries `worktree_space.key`/`is_linked_worktree`
  (`src/workspace.rs:196`) for grouping display; services don't need a second identity axis.

## 5. Alternatives for discovering services

(a) **Explicit CLI/API registration (recommended primary).** Zero new platform/process-tree code;
    matches the existing attribution model (§1) exactly — `herdr service add` inside a pane
    resolves `HERDR_PANE_ID` → workspace, mirroring `caller_pane_id()` (`src/cli/target.rs:157-164`).
    Trivial to test with `AppState::test_new()`. Works identically for remote/SSH-attached
    workspaces where there is no local process tree to inspect at all.

(b) **Automatic TCP-listener detection by scanning the pane process tree.** `src/platform/*` today
    has `ProcessIdentity`/`ProcessHandle` (Windows: `src/platform/windows.rs:643-644,2439-2440`)
    for process handle lifecycle, not a general listening-socket enumerator. `AGENTS.md`
    "Multiplicative performance paths" explicitly bans "inspect process trees" and "perform
    filesystem I/O" inside pane-scaled render/layout loops (`AGENTS.md:47-49`). This rules out any
    scan reachable from render; it would have to be an opt-in, low-frequency **background poll on
    the server** (same shape as §6's liveness probe, or piggybacking on it), walking each pane's
    child processes and probing bound ports (Linux: `/proc/<pid>/net/tcp{,6}` + `readlink
    /proc/<pid>/fd/*`; macOS: `lsof`/`proc_pidinfo`; Windows: `GetExtendedTcpTable`). This is
    real, OS-specific, moderately complex work (three more `src/platform/<os>.rs` implementations)
    for a heuristic result (a process can listen on a port that isn't "the" dev server, or the
    real server can be many process-hops away e.g. behind `docker compose`).

(c) **OSC/terminal escape emitted by the running process.** Would need a new escape sequence,
    parser support in the vendored `libghostty-vt`, and an opt-in convention processes must adopt
    — much larger surface (touches the vendored terminal parser) for the same net registration
    effect as (a), with none of (a)'s "works from any external orchestrator" benefit.

(d) **Config-file declared services per workspace/repo** (e.g. `.herdr/services.toml` in the
    repo root). Static, doesn't reflect actual liveness without the probe anyway, and duplicates
    what registration already models; useful only as a *convenience seed* (auto-register on
    workspace open by reading such a file) layered **on top of** (a), not a replacement.

**Recommendation:** ship (a) as the only registration path for v1. Do not build (b)/(c) now — (b)
in particular fights the explicit render-loop-cost guardrail in `AGENTS.md` and produces
false positives; a config-seed convenience (d) is a reasonable fast-follow once (a) is stable,
not part of this feature.

## 6. Liveness probe

- Model directly on the existing periodic Git-status refresh: deadline-gated, off-thread work,
  event-based reintegration — `src/app/git_refresh.rs:36-53` computes a due deadline
  (`git_refresh_deadline()`, `src/app/git_refresh.rs:95-100`) checked from the same headless loop
  driving other periodic work; `src/app/git_refresh.rs:56-74` spawns `std::thread::spawn` (not
  tokio — this codebase's server loop is a plain OS thread per
  `src/server/headless.rs:265` `std::thread::spawn` for the accept loop) doing the actual
  filesystem/network work off the hot path, and reports back via `event_tx.blocking_send(AppEvent::GitStatusRefreshed { .. })`.
- A `ServiceLivenessProbe` should follow the identical shape: a `service_probe_deadline()` gated
  by "at least one registered service exists and the last probe interval has elapsed" (a few
  seconds — e.g. 5s, distinctly slower than any render/view path), spawn a `std::thread::spawn`
  that does a short-timeout non-blocking TCP connect per registered service URL's host:port, and
  reports `AppEvent::ServiceLivenessProbed { results: Vec<(service_id, bool)> }` back through the
  same channel. Must **never** run from `compute_view()`/`render()` — only from the same headless
  polling loop that drives Git refresh (`src/server/headless.rs`), consistent with
  `AGENTS.md`'s "Multiplicative performance paths" section (`AGENTS.md:38-57`).
- **Persist across restart?** Recommend **yes, but marked stale/down until the first post-restart
  probe confirms liveness** — i.e. persist `ServiceSnapshot { id, label, url, .. }` unconditionally
  (per §3.7's `#[serde(default)]` pattern) but the deserialized live/liveness field always
  restores to `Unknown`/`Down`, never trusts a stale cached "up" value across a restart. This
  matches how e.g. `cached_git_branch`/`cached_git_ahead_behind` on `Workspace`
  (`src/workspace.rs:189-192`) are marked `pub(crate)` cached/derived, recomputed rather than
  trusted, after restore.

## Proposed design

### Data model (server-owned, `AppState`/`Workspace`)

New module `src/service.rs` (parallel to `src/worktree.rs`/`src/workspace.rs`):

```rust
/// A user-registered long-running dev server/listening endpoint owned by a workspace.
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct Service {
    /// Stable id, workspace-scoped monotonic counter — mirrors public_pane_numbers' pattern
    /// (Workspace::next_public_pane_number, src/workspace.rs:201) rather than a global registry.
    pub id: u64,
    pub label: String,
    pub url: String,
    /// Free-text attribution of the registering source, mirrors PaneReportMetadataParams::source
    /// (src/api/schema/panes.rs:481) — "cli", "plugin:<id>", etc. Optional; defaults to "cli".
    pub source: String,
    /// Server-computed; never trusted across a restart (§6). Not serialized to session snapshot
    /// as "true" — always reset to Unknown on restore.
    #[serde(skip)]
    pub liveness: ServiceLiveness,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum ServiceLiveness { #[default] Unknown, Up, Down }
```

Stored as `pub services: Vec<Service>` on `Workspace` (`src/workspace.rs:176-207`), next to
`worktree_space`. `id` allocation: `next_service_id: u64` counter field on `Workspace`, following
the `next_public_pane_number`/`next_public_tab_number` idiom (`src/workspace.rs:201-202`) —
never reused after removal, avoiding stale-id confusion in concurrent add/remove races.

### API methods (neutral server names)

New `Method` variants in `src/api/schema.rs` (near the `Workspace*`/`Pane*` groups):

- `Method::ServiceAdd(ServiceAddParams)` → `"service.add"`
  ```rust
  pub struct ServiceAddParams {
      pub workspace_id: Option<String>,   // omitted => resolve from calling pane, see below
      pub pane_id: Option<String>,        // alternative attribution input from CLI's --current
      pub label: String,
      pub url: String,
      #[serde(default, skip_serializing_if = "Option::is_none")]
      pub source: Option<String>,
  }
  pub struct ServiceAddResult { pub service_id: u64, pub workspace_id: String }
  ```
- `Method::ServiceList(ServiceListParams { pub workspace_id: Option<String> })` → `"service.list"`
  (omitted workspace_id = all workspaces, matching e.g. `WorktreeList` semantics referenced in
  `src/api/mod.rs:38` sibling naming) → `ServiceListResult { pub services: Vec<ServiceListEntry> }`
  where `ServiceListEntry { workspace_id, id, label, url, source, liveness: ServiceLivenessWire }`.
- `Method::ServiceRemove(ServiceRemoveParams { pub workspace_id: String, pub id: u64 })` →
  `"service.remove"`.

Handlers in new `src/app/api/services.rs` (mirrors `src/app/api/panes.rs`/`workspaces.rs`
structure), dispatched from `src/app/api.rs` next to the `WorkspaceReportMetadata`/`PaneReportMetadata`
arms (§3.4). Attribution resolution order in `handle_service_add`: explicit `workspace_id` >
`pane_id` resolved via `self.parse_pane_id()` (same helper used at `src/app/api/panes.rs:1595`) →
owning workspace > error `attribution_required` if neither resolves and CLI/JSON caller supplied
neither.


(`docs/next/website/src/content/docs/cli-reference.mdx:226-230`), erroring with the same

(`src/cli/spec.rs:634-636`); add matching required-option completion entries alongside

### Events

New `AppEvent::ServicesChanged { workspace_id: String }` (coarse — list changed, client re-reads

### Liveness probe

New `src/app/service_liveness.rs` mirroring `src/app/git_refresh.rs`:
- `service_probe_deadline(&self) -> Option<Instant>` — due when any workspace has a non-empty
  `services` and `now >= last_probe + SERVICE_LIVENESS_PROBE_INTERVAL` (propose 5s).
- `start_service_liveness_probe_if_due(&mut self, now: Instant)` spawns `std::thread::spawn`
  performing a short-timeout (~500ms) `TcpStream::connect_timeout` per service URL's resolved
  host:port, reporting `AppEvent::ServiceLivenessProbed` back via `event_tx.blocking_send(..)`
  exactly like `src/app/git_refresh.rs:67-74`.
- Wired into the same headless polling loop as Git refresh (`src/server/headless.rs`) — never
  from `compute_view()`/render.
